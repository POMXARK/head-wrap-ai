# Оценка интерфейса с точки зрения пользователя + сравнение с AstraForge

Дата: 2026-11-06. Оцениваются `/pipeline` (рабочая панель) и `/proto` (прототипы П1–П6).

## 1. Что не так в `/pipeline` (взгляд пользователя)
| Проблема | Почему мешает | Что делать |
|---|---|---|
| Всё построено вокруг шагов конвейера (colormatch, lama_seam…), а не вокруг цели «исправить это место» | пользователь думает «шея светлая», а не «запусти neckblur» | рабочее пространство вокруг модели; шаги — внутри инструмента, как параметры |
| Модель не выбирается в 3D: нельзя ткнуть в место и сказать «тут» | главная задача — точечные правки | выделение области (П2) как первоклассный объект |
| Жаргон: маска, UV, розетка, pad | непонятно без справки | подписи на языке результата: «шея», «шов», «глаз»; термины — во всплывающей подсказке |
| Долгие шаги без прогресса и отмены | непонятно, зависло или работает | прогресс по шагам, кнопка «Отмена», оценка времени |
| Результат применяется сразу | страшно трогать | «до/после», применить отдельной кнопкой, откат одним жестом (журнал) |
| Цвет — единственный сигнал оценки | не видно дальтонику | значок + число + слово |
| Устаревший eye_score.json, профиль сетки только после запуска | показывается неактуальное | считать при открытии, помечать «устарело» |
| Нет замены части одним жестом | главная цель сервиса | П5: перетащить донора на розетку |
| Мобильный вид и клавиатура не проверены | — | проверить; горячие клавиши (Z — отмена, B — кисть) |

## 2. Что учесть в выделении области (по запросу пользователя)
- Выделение — именованный объект (`selections` в `spec/asset.schema.json`), а не временная картинка: «левый глаз» вызывается снова, в том числе ассистентом.
- Три способа: кисть, рамка, «по части» (из `regions.json`); режимы добавить/вычесть, расширить/сузить, инвертировать.
- Выделять надо по **поверхности**, а не по 2D-экрану: не захватывать то, что закрыто (задняя сторона головы, другая сторона носа). Кисть работает по видимым граням + «сквозное» включается явно.
- Растушёвка края в мм (`feather_mm`), чтобы правка не оставляла шов.
- Инструмент и ассистент меняют только внутри области (`op.selection`); вне — затемнено и защищено.
- Хранение в двух видах: вершины (для геометрии) и маска в UV (для текстуры) — один и тот же выбор должен работать для обоих.

## 3. Сравнение с AstraForge (v0.4.x, по README и сайту; сам не запускал)
AstraForge (Snodrod/AstraForge, Windows + NVIDIA, локально, UI на en/ru) — **генератор**: картинка/текст → 3D (Hunyuan3D) → текстуры → риг → анимации → эффекты → Godot-пакет/спрайты. Объём установки ~30 ГБ (быстрая) / ~95–135 ГБ (полная), легкая ~3 ГБ.

| Возможность | AstraForge | Наш сервис (цель) |
|---|---|---|
| Создание модели с нуля из картинки/текста | да (главное) | нет, не цель |
| Правка готовой модели | импорт GLB/OBJ/STL; перемещение/поворот/масштаб, цвет, материал, примитивы, undo/redo | правка конкретных дефектов с оценкой качества |
| Выделение области / маска | **не описано**; нет вершинной правки и скульптинга (явно в списке «не поддерживается») | выделение — основа |
| Замена части (голову на тело) | прямо не заявлено; возможно через «Forge/kitbash» в Blender | главный жест (П5) |
| Критики качества (оценка глаз/сетки) | нет | есть, объясняют результат |
| ИИ-помощник | Ollama/OpenAI/Anthropic, только ограниченный набор проверенных действий | агент + обучение на правках пользователя и RL локально |
| Рига/анимации/эффекты | да | позже, перенос весов при замене части |
| Выход | GLB, OBJ, WebM, PNG, Godot, спрайты | GLB и игровой .gm |
| Лицензия | бесплатно для некоммерческого (PolyForm NC с 0.4.2), коммерческое — $5/мес | своё |

Вывод: AstraForge не конкурент, а **дополнение**: он делает новые модели, мы — управляемо чиним/пересобираем существующие. Что перенять: один экран-пайплайн со статусами этапов, горячие клавиши (W/E/R, Ctrl+Z), установщик со сканом ПК, ограниченный набор проверенных действий ассистента (у нас это схема операций `op.schema.json`), локальный сервер 127.0.0.1, ru/en. Чего у них нет и мы делаем: выделение области, замена части по розеткам, критики, обучение на правках.

Asset Forge (Kenney, $19.95) — киткашинг блоков, не про органические модели; пробной версии нет, сравнение только по описанию.

Не скачивал: установщик AstraForge 30+ ГБ потребовал бы Windows-машины и подтверждения пользователя; сравнение сделано по публичным README и сайту. Если нужно сравнение «руками» — поставить «Light» (~3 ГБ) или «Quick» на Windows-машину.

## 4. Проверка вживую: AstraForge 0.4.16 на Windows (2026-11-06)
Установлен в `C:\AstraForge` (профиль «лёгкий»). Запускал `runtime\node\node.exe server\index.mjs` через ssh-сессию, порт 3210 пробросил на Linux, снимал headless Chrome (3D-вид в снимке пуст — программный GL; панели видны).

Что видно в интерфейсе:
- Три колонки: слева **рабочее пространство** (вкладки-этапы: Создать, Кузница, Кости, Текстуры, Скульпт, Анимация, Эффекты, VFX, Спрайты, 2D, AI, Tripo), в центре 3D-вид с тулбаром (выбор / перемещение / вращение / масштаб / вписать), справа **список объектов сцены** (иерархия с глазками видимости) и свойства выбранного.
- Внизу таймлайн анимации; сверху: Проекты, Сохранить, Экспорт, undo/redo, скриншот, сетка.
- Подсказки горячих клавиш в правой панели (W/E/R/F); статус локального движка и GPU — карточкой справа внизу; подсказки мышью в углу вида.
- Каждый этап — короткий мастер: заголовок («Начните с идеи»), выбор «Что создаём?» (существо/предмет/корабль), загрузка изображения, ракурсы.
- Вкладка «Скульпт» есть: встроенный SculptGL (в 0.4.16; README старой версии это отрицает) — в отдельном окне, не в общем виде.
- Редактирование идёт по **объектам** (фюзеляж, кабина, крыло…), а не по области на поверхности: выделение по вершинам/маске в главном виде не нашёл (по исходникам смотрел только sculpt-файлы).

Выводы для нас:
1. Перенять: левая колонка этапов + центральный вид + правый список частей; undo/redo и скриншот в шапке; подсказки клавиш рядом; статус локального движка; мастер «заголовок → выбор → загрузка».
2. Список частей справа с глазками — готовая модель для «замены части» (П5): часть = строка списка, замену делать на строке.
3. Наш плюс: выделение области на поверхности, оценка «до/после» критиками, обучение на правках — у них этого нет. Скульпт у них отдельным окном — наш выбор области должен быть в основном виде.
4. Их слабое место: 12 вкладок — новичку неясно, с чего начать; нам держать 3–4 режима (Выделить / Править / Заменить / Сравнить).

## B3.1 (2026-11-06): долгие шаги
Замена головы идёт фоновой задачей: полоса прогресса, этап словами, оценка оставшегося времени, «Отмена» (модель не меняется до финального применения).

## B3.2: до/после
Кнопка «Показать «до»» переключает вид на состояние до последней правки; применять заново не нужно, откат остаётся «Отменить».

## B3.3: устаревшие оценки
Если модель или настройки новее оценки — красный баннер «Оценка устарела: …» над таблицей; в журнале /edit оценка помечена, когда после неё были правки.

## C2: совет помощника
Кнопка «Посоветовать» показывает до 3 вариантов сглаживания выделенной области с объяснением («шероховатость N% от исходной, сдвиг M длины ребра»); «Взять» подставляет параметры, применяет пользователь.

## C3: лог правок
Интерфейс не менялся: каждая правка тихо пишется в локальный журнал; «Отменить» считается сигналом «не понравилось».

## 5. Переделка `/edit` по правилам UX/UI (2026-11-06)
Источники правил: [Nielsen/Molich: 10 эвристик](https://ixdf.org/literature/article/user-interface-design-guidelines-10-rules-of-thumb), [Figma: принципы UI](https://www.figma.com/resource-library/ui-design-principles/), разбор эвристик для интерактивных редакторов (состояние и режим всегда видны; подсказки жестов видимы, а не в тексте; главная рабочая поверхность — самая заметная; прогрессивное раскрытие).

| Правило | Что было плохо | Что сделано |
|---|---|---|
| Видимость состояния | инструмент/режим — кнопки-переключатели с меняющимся текстом, счётчик внизу мелким серым | панель инструментов слева (Кисть B / Рамка X / Вид R) с нажатым состоянием; чип «Выделено: N» поверх вида; строка состояния снизу |
| Распознавание, а не запоминание | инструкция одной строкой в шапке | подсказки мыши и клавиш на самом виде, меняются с инструментом |
| Иерархия | всё одинаковые кнопки, зелёная «Применить» тонула | один главный акцент (синяя «Применить» и «Заменить голову»), остальное — второстепенные; вид занимает всё свободное место |
| Группировка и порядок шагов | два свалка кнопок | правая панель по шагам: 1 Область → 2 Правка → 3 Заменить голову → Журнал; разделы сворачиваются |
| Прогрессивное раскрытие | все ползунки всегда | для «Сгладить» виден только счётчик итераций, для «Сместить» — только сдвиг; размер кисти только при кисти |
| Предотвращение ошибок | «Применить» без выделения | кнопка недоступна и подписана почему; «Отменить» недоступна без правок |
| Обратная связь | `alert()` | уведомления-тосты, ошибки красные и дольше; «Применено — Z вернёт как было» |
| Контроль и свобода | Esc не работал | Esc — снять выделение, Z / Shift+Z — отмена/возврат |
| Контраст и размеры | серый текст, мелкие кнопки | токены цвета с контрастом ≥ 4.5:1, цели нажатия ≥ 36 px, шаг 8 px, видимый фокус, тёмная тема, `prefers-reduced-motion` |
| Устойчивость | без WebGL страница молча пустая | сообщение «3D-вид недоступен», остальной интерфейс работает |

Проверено: кадр headless Chrome (1400×900), дымовой прогон: часть «нос» → 913 вершин, «Применить» включается, «Сместить» прячет ползунок итераций, правка попала в журнал, отмена вернула. Тест `tests/test_edit_ui.py` (статические правила). Реальной мышью проверить не удалось: Chrome на этой машине не создаёт WebGL-контекст (при новом запуске требует принять условия Google — не принимал за вас).

Дополнение: Z / Ctrl+Z / Shift+Z / Y сначала отменяют и возвращают шаги выделения (мазок кистью, рамка, расширить, снять…), и только когда их нет — правку модели. Кнопки «↶ Шаг назад / ↷ Шаг вперёд» в разделе «Область»; кнопки сверху названы «Отменить правку / Вернуть правку». Раньше Z отменял только правку модели, а она недоступна, пока ничего не применено, — поэтому «отмена не работала». Сервер: `select` action `set` (точное восстановление выделения), тест `tests/test_selection_undo.py`.

## 6. Переделка `/pipeline` (2026-11-06)
Была страница-простыня: справка на пол-экрана, таблица кнопок с длинными описаниями, 20 настроек, журнал, таблицы — всё одним столбцом; `alert()`, цвет как единственный сигнал, «В игру» без подтверждения.
Стало (файл `pipeline.html`, отдаётся через `pipeline.PAGE`): три колонки как в `/edit`.

Тест `tests/test_pipeline_ui.py`; кадры headless Chrome 1500×900 (вкладки «Оценка» и «Настройки»).

## 7. Инструменты скульптинга, текстуры и UV в `/edit` (2026-11-06)
Запрос: «не вижу инструмента редактирования текстуры и UV и растягивания сетки — основные инструменты Blender/ZBrush».
Что добавлено (логика в `ops.py`, `texture.py`, `edit_api.py`; интерфейс в `edit.html`):
- **Правка сетки** (раздел «2. Правка», 6 кнопок): Сгладить, Сместить (X/Y/Z), **Надуть** (Inflate, по нормалям, ±), **Выровнять** (Flatten, к средней плоскости), **Сжать** (Pinch, к центру вдоль поверхности), **Растянуть** (Scale по осям от центра области). Все работают по выделенной области с мягким краем; вне области вершины не двигаются (общая гарантия `ops.apply`).
- **Двигать (G)** — как Grab: потяните выделенное в плоскости экрана; при отпускании одна правка (одна отмена), край смягчается ползунком «Мягкость края».
- **Симметрия по X** для кисти выделения.
- **Вид «Текстура»** — голова с текстурой, выделение подсвечено; инструмент **Рисовать (P)** красит прямо по модели (попадание → UV). Режимы кисти: Краска (цвет), Стёрка (возврат к оригиналу), Размыть, Светлее, Темнее; размер в пикселях, сила.
- **Вид «UV»** — развёртка поверх текстуры (колесо — масштаб, ПКМ/«Вид» — сдвиг), выделенные грани подсвечены, рисовать можно и тут.
- **Раздел «4. UV»**: сдвиг, растяжение (ширина/высота), поворот развёртки выделенного места; остальные UV не меняются.
- Одна история для текстуры и UV (кнопки ↶/↷ в разделе «Текстура», Z в видах «Текстура»/«UV»). «Сохранить в work/head_edit.*» пишет `head_edit.png` и `head_edit.obj`; оригиналы (`work/baked.png`, `template/head_sub.obj`) не перезаписываются (проверяется тестом по md5).
- После «Заменить голову» текстура и UV переносятся от донора (если в файле есть UV; нет текстуры — серая). У каждой топологии своё состояние и история текстуры (реестр в `texture.py`). Если у донора нет UV, «Текстура»/«UV» недоступны с причиной в подсказке, а открытый вид сам возвращается на «Сетка» с уведомлением.
Наше упрощение: текстура — `work/baked.png` (1024², одна), UV правятся по вершинам области (вершина на шве двигает все свои UV-копии, острова не разделяются).
Чего ещё нет: маска (Mask), кисть-«Grab» с мазком в реальном времени по серверу (сейчас предпросмотр только выделенных вершин), клонирование текстуры, слои, редактор отдельных UV-островов по клику.
Тесты: `test_sculpt_ops.py`, `test_texture_uv.py`, `test_edit_tools_api.py`, `test_edit_tools_ui.py`. Кадры: `docs/img/edit-texture.png`, `docs/img/edit-uv.png` (headless Chrome 1500×900; дымовой прогон: все 6 правок, вид «Текстура», мазок, UV сдвиг/растяжение/поворот, отмена, вид «UV» — без ошибок).

## 8. Импорт и экспорт в `/edit` (2026-11-06)
Вопрос пользователя: почему нет импорта и экспорта, нельзя взять данные из игры. Причина: `model.py`/`/model` умели импорт GLB и вынос частей, а `/edit` работал только с шаблоном головы и фиксированным донором `hero1`; «проводника» (обзора файлов) в проекте нет — его роль теперь играет кнопка «Файл» и список источников.
Что сделано:
- **Источники импорта** (раздел «5. Импорт головы», список строится сервером, `edit_api.sources`): шаблон; файлы `work/`, `work/imported/`, `models/` (`.glb/.gltf/.obj`); **модели игры** `pdm-game/data/ai_models/orig/characters/*.gm` — переводятся игровым конвертером `tools/pdm_gm2glb.py --no-rig` в `work/imported/<имя>.glb` (один раз) и дальше как обычный файл.
- Выбор **части файла**: у GLB несколько мешей (у игровых моделей голова, торс, волосы…), список показывает число вершин, по умолчанию крупнейшая; голова в игровой модели обычно `*_head_0`.
- **Загрузка с компьютера** (кнопка «Файл»): файл уходит в `models/` (до 64 МБ, только `.glb/.gltf/.obj`, имя очищается), сразу выбирается как источник.

## 13. «Ремеш и UV»: зачем, что получится, как откатить
Замечание: непонятно, зачем панель, что получится и как откатить. Нарушены правила «видимость состояния», «предсказуемость» и «отмена» (§1 ux-rules).

Причины: (1) UV, выходящие за 0..1 (тайлинг), сворачивались `mod 1` по вершинам — треугольники на границе рвались; теперь UV считаются по углам и треугольник сдвигается целиком; (2) соседние ячейки атласа подмешивались на границах — UV отступают на 0,2% от края ячейки; (3) PNG атласа уменьшался до 1024 px (ячейка ~200 px) — теперь до 2560. Заодно: камера предпросмотра ближе (3,5 R), кнопка «⟲ 180°» — у игровых моделей перед часто смотрит от камеры.

## 27. Грани на модели: всегда сглажено, без переключателя

Замечание: на текстурированном виде видны треугольники, в игре граней нет; нужен параметр сглаживания. Причина: неиндексная геометрия (углы + UV) получала нормали через `computeVertexNormals` — плоские, по одной на треугольник. Теперь сервер отдаёт сглаженные нормали, посчитанные по сварной сетке (шов UV не даёт граней); угол с нулевой нормалью или нормалью «внутрь» (части с разной обмоткой) берёт нормаль своей грани — иначе тело чернело. В редакторе нормали берутся из индексной сетки. Отдельного переключателя нет: в Blender его в виде нет (там грани зависят от нормалей модели, а не от настройки вида), поэтому сглаживание всегда включено; первоначально добавленный чекбокс «Гладко» убран по замечанию. `render.py` (2D-виды для генерации изображений) тоже освещает по сглаженным нормалям (`smooth=True`, `False` — прежний гранёный вид). Не тронуто: `tools/pdm_model_views.py` из corsairs-remake рисует виды игры — там своё затенение, в этом репозитории его нет.

## 28. «Вся модель» из игры: нормали файла, без склейки частей, вырезы по альфе

Скриншот: на лице светлые угловые пятна, в глазах рыжие искры. Смотрели, как сделан импорт из игры (`corsairs-remake/tools/pdm_gm2glb.py`): в GLB пишутся собственные нормали игры (`NORMAL`) и `alphaMode: MASK`, а виды (`pdm_model_views.py`) освещаются по ним. Наш слияние частей делало иначе: (1) вершины сваривались по координате между частями, и нормали глаз, кожи и волос смешивались → пятна и искры; (2) нормали считались заново; (3) альфа текстуры терялась (`convert('RGB')`). Теперь `_merge_all`: сварка только внутри части (швы UV), части друг с другом не склеиваются; предпросмотр берёт нормали из файла (`vn`); грани с прозрачным UV (RGBA < 128) в атлас не попадают. Проверено в Chrome на `work/imported/hero.glb` (все части): лицо без пятен и искр. Остаётся: светлые «овалы» кожи вокруг глаз — это отдельные части самого файла (веки), не артефакт слияния; нормали файла в основном виде редактора пока считаются заново (но без смешивания частей).

Версия кода сервера показана в нижней строке окна «Редактирование» («версия abc1234»): по ней видно, обновились ли `git pull` и перезапуск (маршрут `/api/version`). Сверяйте с последним коммитом на GitHub перед тем, как сообщать о баге.

## 29. Основной вид редактора: гранёность и искры в глазах

Скриншот с версией 2a5004e: предпросмотр импорта чистый, но в самом редакторе («Сетка», «Сплошная» и «Текстура») модель гранёная, в глазах искры. Причины: (1) редактор пересчитывал нормали по сетке (`computeVertexNormals`), а предпросмотр брал нормали файла; (2) глаза и веки лежат почти на одной поверхности, и глубины не хватало (z-fighting): `near` камеры считался один раз при кадрировании, а не от расстояния до модели.
Сделано: `replace_prepare` в режиме «как есть» сохраняет нормали файла (`HEAD_VN`), `mesh()` отдаёт их, пока голова не менялась (после правки или отмены остаётся пересчёт); основная камера обновляет `near/far` от расстояния до цели; материалам сетки и текстуры добавлен `polygonOffset`. Проверено в Chrome на Linux (hero.glb, «Вся модель»): светлого/гранёного шейдинга нет. На Windows и реальных `chars_rig\models` не проверялось.

## 30. Вырезы текстуры (ресницы, глаза) в основном виде

Скриншот: в «Текстура» вокруг глаз полосатые прямоугольники, в Blender их нет. Причина: атлас и текстура редактора хранились как RGB, прозрачные места файла показывали цвет «под» ними. Теперь атлас RGBA, `texture.register` помнит альфу, `/api/edit/texture.png` отдаёт RGBA, материалы редактора и предпросмотра с `alphaTest: .5`. Проверено в Chrome на Linux (hero.glb, «Вся модель»); на Windows не проверялось.

## 31. «Вся модель» из игры: тайлинг UV и отсечение задних граней

Файл `hero.glb` из игры (Cap_*) содержит двусторонние дубликаты граней (≈2286 пар с обратной обмоткой и тем же UV) и слои глаз почти в одной плоскости. При `DoubleSide` они давали z-fighting и тёмные квады от глаз к носу; игра и Blender рисуют односторонне.
- `_merge_all`: части с UV вне 0..1 (hvostik, u до 1.35) тайлятся в ячейке атласа (до 4×4), а не обрезаются.
- `mesh()` отдаёт `cull=true`, пока меш совпадает с загруженным из файла; `edit.html` ставит `FrontSide` (и в предпросмотре для glb/gm:/ext:).
- Результат на Linux (SwiftShader): большие квады исчезли.
- Осталось: мелкая тёмная штриховка у век/бровей (вероятно карточки с альфой, которой нет в RGB-текстуре, и плотные слои глаз). Не решено.
- На Windows не проверялось.

### 31а. Штриховка у глаз — причина найдена
- `hero.glb` из игры: полоса глаз в голове (Cap_) — ~15 тыс. граней, ~22 грани на ячейку 2 мм по глубине 1 мм (≈11 слоёв, около 40 % смотрят внутрь, 3540 крошечных граней). Это слои для моргания движка (строки окна глаза), а не ошибка генератора `eye_patch.py`.
- Слои дают одну и ту же текстуру, но разные нормали: при освещении Standard-материал показывал z-fighting как тёмную штриховку; без освещения (MeshBasic) лицо чистое (проверено в Chrome).
- Исправление: для моделей из файла (`cull`) режим «Текстура» рисуется MeshBasicMaterial (без освещения, как в предпросмотре Blender); «Сплошная» остаётся освещённой.

## 32. Части файла: скрыть и выделить
- «Вся модель» сливала части файла в одну сетку, границы терялись. `_merge_all` теперь отдаёт `parts` = [имя, v0, v1] (диапазоны вершин), `mesh()` передаёт их, пока меш совпадает с файлом.
- Панель «1. Область» → «Части модели»: кнопка 👁 скрывает/показывает часть (фильтрация индекса для сетки и текстурного меша; кисть и рамка скрытое не трогают), клик по имени выделяет всю часть, «Показать все».
- Проверено в Chrome на hero.glb: 17 частей, скрытие торса и пояса видно в режимах Сетка/Текстура.

## 33. Части файла: понятные имена, множественный выбор, подсветка, призраки
- Почему `Cap_`, `Cap__1`…: это имена объектов из экспортёра игры (3ds Max), по ним ничего не понять. Осмысленное имя есть в текстуре материала: `hero_arm_top.tga` → «Плечо». `_part_labels` (edit_api.py) переводит слова текстуры (head, arm_top, leg_bottom, palash …) и добавляет сторону конечности по знаку X (модель смотрит в −Z, +X — её правая сторона); две части с одной текстурой различаются «(верх)/(низ)». Если слова нет в словаре — показывается имя текстуры как есть.
- Нейросеть для имён не подключена: для частей игры достаточно текстур, а вердикт по картинке был бы догадкой. Второе имя — своё: кнопка ✎ у строки (хранится в localStorage браузера, ключ имя+размер части).
- Список: клик — выбрать, Ctrl/Shift+клик — несколько; наведение подсвечивает часть в окне, выбранные — оранжевые; кнопки «Только эти», «Скрыть эти», «Показать все», «Призраки» (скрытые — полупрозрачные), «В выделение» (вершины выбранных частей → кисть, режим Добавить/Вычесть).
- Подсветка и призраки — отдельные меши поверх (MeshBasic, transparent, raycast отключён), модель не меняют.
- Проверено в Chrome на hero.glb (17 частей).
